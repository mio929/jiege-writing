# 插图与图注

课程论文的图只有三条来路，按优先级排：自己的实测数据 → 文献原图 → 自己画的示意图。**不要用图像生成模型造图**，哪怕只是「示意图」。评审看到一张没有出处的机制图，第一反应是这张图从哪抄的；生成图既不能标注来源，也无法复核，等于给自己埋雷。

## 1. 三条来路

| 来路 | 适用 | 图注要写 | 风险 |
|---|---|---|---|
| 实测数据 | 有实验或调查数据 | 数据来源、样本数、误差线含义 | 无 |
| 文献原图 | 综述、方法学评述 | `（引自文献[n]）` | 版权；图内文字是英文 |
| 自绘示意图 | 无合适文献图，且逻辑自己能讲清 | `（据文献[n] 改绘）`，并说明哪些部分是自己归纳的 | 容易被当成「编的」 |

实测数据用 `scripts/plot_style.py` 出图，字体、刻度、轴范围都有约束，见 SKILL.md「图表规范」。

文献原图优先选开放获取（OA）的，取图不违规，图注写明出处即可。订阅期刊的图不要破解下载，换一篇 OA 文献，或者改成自绘并注明「据文献改绘」。

## 2. 从 OA 文献取图

`scripts/fetch_pmc_figs.py` 走 PMC，两步：eutils 取图题与文件名，再从文章页的 `cdn.ncbi.nlm.nih.gov/pmc/blobs/...` 拿真实地址。直接拼 `/bin/文件名` 现在 403。

```bash
python scripts/fetch_pmc_figs.py PMC7460318 --list          # 先看图题，挑图
python scripts/fetch_pmc_figs.py PMC7460318 -o figs/ --only g004
```

挑图的四条标准：

1. **图题能对上论文章节**。别为了凑数硬塞，图与正文对不上比没有图更糟。
2. **原图分辨率够**。PMC 的图多在 780–800 px 宽，印到 12 cm 约 165 dpi，够用；低于 600 px 的，缩到 10 cm 以内还好，放大就糊。
3. **图内文字是英文**。中文课程论文里放英文图可以接受，图注用中文把每个面板讲清楚。
4. **配色与全文协调**。四张图来自三篇文献，风格不可能统一，靠图注格式统一视觉：一律 `Figure N` + 中文说明 + 9 pt 居中。

MDPI、Frontiers、PLOS 的图有 Cloudflare 拦截，直接下会 403，走 PMC 更稳。Nature 系列的部分子刊在 PMC 有全文，同样适用。

**版权**：课程作业内部使用，标注出处即可。要投稿或公开出版，CC BY 需保留署名与许可声明，其他协议要取得授权——这一步必须提醒用户，不要替他决定。

## 3. 图注怎么写

格式跟正文分工：正文用「图 1」，图注以 `Figure 1` 起头。这是中文期刊的通行做法（图题英文、正文指代中文），也贴合多数学校模板。学校明确要求全中文时，把 `Figure` 换成「图」即可，改一处。

```
Figure 1　重金属进入农田土壤的六类人为来源（引自文献[7]）
Figure 2　矿区河流两岸农田土壤细菌（a）与古菌（b）在门水平的相对丰度。
          样点间的组成差异反映了重金属与养分条件的共同选择（引自文献[15]）
```

四条硬规则：

- **编号与正文一致**。图注里的文献编号必须与正文编号同一套。图注里写 `@key@`，脚本按正文首次出现顺序换成 `[n]`；写成 `{{key}}` 会打乱排序，因为图注也参与「首次出现」的判定。
- **图注自身 9 pt、居中、单倍行距**，比正文小一档。全文统一，不要一张图一种字号。
- **一张图配一句话结论**，不要只写「××示意图」。读者跳过正文也能看懂这张图在论证什么。
- **多面板要逐个交代**。(a)(b) 或 A/B/C 分别是什么，写在图注里，不要指望读者去猜。

## 4. 插入流程

图不能直接塞进 `build_docx.py` 的 blocks（它只产出段落）。用占位段 + 后处理：

**第一步**，在 spec 里放两个相邻的段落占位：

```json
["p", "__FIG_1__"],
["p", "__CAP_1__Figure 1　重金属进入农田土壤的六类人为来源（引自文献@alengebawy2021@）"],
```

**第二步**，在 spec 顶层写图片路径与宽度（宽度单位 cm，不超过版心 14.66）：

```json
"figures": {
  "1": {"src": "figs/PMC7996329_g001.jpg", "width_cm": 8.6}
}
```

**第三步**，构建后跑脚本：

```bash
python scripts/build_docx.py spec.json -o draft.docx
python scripts/insert_figs.py spec.json draft.docx --check      # 先核对图注与编号
python scripts/insert_figs.py spec.json draft.docx -o final.docx
```

`--check` 会列出「图号 / 宽度 / 文件名 / 最终图注」，编号错了在这一步就能看出来。

## 5. 为什么包一层表格

Word 的「与下段同页」（`keepNext`）对含图片的段落**不可靠**。实测：图片 11.5 cm，页底只剩 6 cm，Word 把图留在页底、图注推到下一页，`keepNext` 形同虚设。

把图和图注写进**同一个段落**（图 + 换行 + 文字）也不行：图片作为内嵌对象不计入行高，图注文字会压在图片下缘上，压掉 5–8 mm。

可行解是**无边框单格表格**：

- 图和图注各占单元格内一个段落；
- 表格边框全 none，单元格内边距归零，肉眼看不出来；
- 行属性加 `<w:cantSplit/>`，整行不允许跨页 —— 这才是真正把两者绑在一起的东西。

`insert_figs.py` 已按这个结构生成，不要再手写。

## 6. 尺寸与分辨率

| 图宽 | 原图 800 px 时的有效 dpi | 判断 |
|---|---|---|
| 8–10 cm | 200–250 | 清晰 |
| 12 cm | 165 | 可用，图内 6 pt 字仍可辨 |
| 14 cm | 145 | 下限，图内小字开始糊 |

版心 14.66 cm（21 − 3.17×2）。超过就会被 Word 压回版心并留下空白。

判断「图内文字能不能看清」的土办法：按目标宽度把图插进 Word，导出 PDF，100% 缩放看一眼轴标签。看不清就换图或者裁掉不重要的面板。

## 7. 四个故障

| 现象 | 成因 | 改法 |
|---|---|---|
| 图在页底、图注跑到下一页 | `keepNext` 对含图段落失效 | 表格包裹 + `cantSplit` |
| 图注压住图片下缘 | 图与图注写在同一段落，图片不计入行高 | 拆成单元格内两个段落 |
| 图注里的编号与正文对不上 | 图注用了 `{{key}}`，参与了首次出现排序 | 改 `@key@`，编号由脚本按正文重算 |
| 图被压缩、右侧留白 | 插入宽度超过版心 | 宽度 ≤ 14.2 cm，表格列宽也设 14.2 |

## 8. 一次实测的账

一篇 13 页课程论文，4 张文献图，全部 OA 来源：

| 项 | 值 |
|---|---|
| 图 | 4 张（8.6 / 10.4 / 12.8 / 12.8 cm） |
| 图注字数 | 26–56 字，两行以内 |
| 图注字号 | 9 pt，居中，单倍行距 |
| 取图耗时 | 约 20 分钟（含挑图、看图题、核对来源） |
| 排版返工 | 3 次（分页 → 重叠 → 表格方案） |
| 交付页数 | 13 页，正文 6865 汉字 |

返工都花在第 5 节那两个坑上。先按表格方案做，一次就过。
